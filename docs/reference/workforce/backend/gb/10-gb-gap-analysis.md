# Qnipay Workforce on GB Qnipay: gap analysis

2026-10-26 · Status: draft for review

This document checks the Business Central backend design for the Qnipay Workforce app (01–06 in the parent folder, written against W1) against the **GB** Qnipay codebase, and says what changes. Five reviewers each checked one area (foundation, access and configuration; people and dimensions; timesheet and clocking; onboarding; posting to payroll). This document merges their findings, applies the integrator's rulings, and records every decision and open question.

Companion documents:

- [`11-gb-new-tables.md`](11-gb-new-tables.md): the object register with real IDs, the new tables, the fields added to existing tables, enums and events.
- [`12-gb-field-mapping.md`](12-gb-field-mapping.md): every contract field mapped to a GB table and field.
- [`13-gb-api-endpoints.md`](13-gb-api-endpoints.md): the API, the command catalogue and the map of all 122 `/api/v1` operations.

Source checked: `C:\dev\Qnipay GB BC`, apps `Qnipay-base` ("Qnipay Base" 26.0.9.1) and `Qnipay-GB` ("Qnipay" 26.0.9.1), publisher Dogma Group. Paths: `B/` = `Qnipay-base\SourceCode\`, `G/` = `Qnipay-GB\SourceCode\`; "MS" = the Microsoft Base Application 29.0.54011.56136 symbols in `.alpackages`; "BC base app" means a standard Microsoft table that is not in the GB source. Contract truth: `docs/superpowers/handoff/backend-inputs.md` and `src/contract/*.ts`. Decisions are GB-D*n* (§10), questions GB-Q*n* (§11), contract changes C*n* (§9).

## 1. Summary

**Verdict.** The design carries over to GB. Its approach holds (Node decides, Business Central commits; a Workforce day separate from payroll's timesheet documents; posting through payroll's own inbound interface), but its shape changes in many places, because Workforce now lives inside Qnipay Base instead of a separate app, and because GB differs from W1. Everything in the first product fits in Base's ID range 70703150–70703299. One payroll change is needed before posting can go live (problem G: the GB interface has no pay period), and two more should come with it (A, rates; B, Daily mode). Six questions decide the most: GB-Q22 (pay period fields), GB-Q37 (licensing), GB-Q1 (starter declaration), GB-Q2 (on leave stops pay), GB-Q3 (timesheet lock) and GB-Q23 (rates).

Most important findings:

1. **Packaging changes the shape of every extension (AL0334).** An app cannot extend its own table or extend the same target twice. With Workforce inside Base, fields go into Base's own tables (`SIR Feature Register`, `SIR Notification Entry`, `SIR Work Sites`, `SIR TIme Sheet Elements`, the two timesheet interface tables) and into Base's existing extensions of Employee, Employee Relative and Base Calendar Change. Only five standard tables get new extensions. 01 §8's `SIR_WF Employee`, `SIR_WF Employee Relative`, `SIR_WF Notification Entry`, `SIR_WF TS Interface` and `SIR_WF Work Sites` extensions cannot exist (§2.1).
2. **GB has no session, no Entra link and no portal users.** `SIR Approval Session` and `SIR Approver Entra Object ID` exist only in W1. New tables 70703152 `SIR_WF Account` and 70703153 `SIR_WF Session` carry identity and view-as; employees stay portal users, not BC users (§2.5).
3. **Commands: bound actions with parameters already work in GB.** `G/API Pages/Pag70702818.SIRGBPayslipAPI.al:108-117` has a `[ServiceEnabled]` action with a parameter and a Text result. Workforce uses bound actions wherever a record exists, and one generic `commands` page for the rest: 15 commands on the page, 33 bound actions, 48 command types in all, one handler codeunit each. This saves about 30 page IDs over 03's command entity sets (§2.4).
4. **The ID block holds the first product, with pages the tight type.** 55 tables, 68 API pages, 77 codeunits, 41 enums, 1 query, 5 table extensions and 3 permission sets in 70703150–70703299; 50 page IDs are reserved for the BC client pages B7 needs. Rota, Leave and Notices later will press pages hardest (§2.2).
5. **Posting: the GB interface is older than W1's.** No pay period on the row (G), so Create Time Sheets sweeps every pending row into the one period chosen; Daily mode is the default and multiplies hours by the days in the period (B); a zero rate stops the whole run and the only rate source is an interactive action (A). G needs a Base change; until then the fallback narrows but does not close the risk (§8).
6. **The contract has lost its posting surface.** `IntegrationAttempt`, the posting log and retry and the `integration` capability were cut (`docs/superpowers/cuts.md:141-167`), and `src/contract/contract.test.ts:118` forbids `/api/v1/integration`. Posting is in the first product, so they must come back (§9, C1).
7. **GB payroll reacts to Workforce writes.** An `Inactive` employee is left out of the payroll run (`B/Codeunit/Cod70702575.SIRPayrollBaseEngine.al:182-190`), so on leave and suspended would stop pay; GB refuses `_` in employee codes (`G/Subscribers/Table Helpers/Cod70702733.SIRGBEmployeeHelpers.al:196-210`); a preferred bank code copies bank details onto Employee for BACS (`B/Table Extensions/Tab-Ext70702579.SIREmployee.al:308-337`); Company Information and the timesheet base calendar feed payslips, HMRC and working-day counts (§4, §3).
8. **GB onboarding has a home already.** The HMRC starter checklist (`G/Table/Tab70702735.SIRGBStarterChecklist.al`) takes the Workforce starter at start through a GB subscriber to three Base events. But the contract collects only the NI number, so without a GB declaration step every Workforce starter falls back to declaration C (GB-Q1). Files go to Blob Storage, never into BC (§6).
9. **Timesheet: the W1 day model holds, with GB-specific locks.** The day, entry, break and log tables carry over; a new week row holds the aggregate version (R2). The posted-period lock reads `SIR Pay Period.Posted`, a FlowField over the money table `SIR Payroll Ledger Entry` (`B/Table/Tab70702586.SIRPayPeriod.al:82-91`), so it is read through a codeunit with indirect permission (§5).
10. **Workforce calls no `dogma/payroll` page.** The GB API pages expose money, unmasked bank details, and no versions, and Base cannot depend on GB. The financial year, pay frequency, bank holidays and work sites are read through Workforce's own pages (§2.3, doc 13 §9).

## 2. Cross-cutting findings

### 2.1 Packaging and AL0334

The user settled the packaging: no separate Workforce extension; Workforce objects go inside Qnipay-base, GB-only parts in Qnipay-GB (GB-D1). The AL compiler then forbids an app to extend its own table, or to add a second extension to a target it already extends (AL0334). The rules that follow (GB-D7):

- **Base-owned tables** get Workforce fields in the table itself, named `SIR_WF …`: `SIR Feature Register` 70702660, `SIR Notification Entry` 70702657, `SIR Work Sites` 70702606, `SIR TIme Sheet Elements` 70702615, `SIR Timesheet Interface` 70702614, `SIR Posted Timesheet Interface` 70702661. The same holds for Base-owned enums: `SIR Notification Type` 70702594 gets its new value inside the enum.
- **Employee, Employee Relative and Base Calendar Change** get Workforce fields inside Base's existing extensions 70702579 `SIR Employee`, 70702583 `SIR Employee Relative`, 70702581 `SIR Base Calender Changes`.
- **Standard tables Base does not extend** get new Base table extensions. `grep tableextension` over Qnipay-base finds nine extensions: G/L Entry, Gen. Journal Line, Reversal Entry, Source Code Setup, Employee, Human Resources Setup, Base Calendar Change, Approval Entry (`B/WorkFlows/Table Extension/Tab-Ext70702582.SIRApprovalEntry.al`), Employee Relative. So Dimension Value, Job, Job Task, Employee Qualification and Document Attachment are free to extend: 70703150–70703154. Company Information needs no change.
- **Consequence.** Moving these fields to a separate Workforce app later needs a data move (table or field move, or an upgrade codeunit). Doc 11 §7 keeps the list of every `SIR_WF` field on a Base object.
- **Base changes need the payroll owner.** Even inside one app, a change to an existing payroll object (the feature register, the interface tables, the creation report) is the payroll owner's to agree (§8).

### 2.3 The API route

Every slice agreed on publisher `dogma`, group `workforce`, version `v1.0`: `/api/dogma/workforce/v1.0/companies({id})/…` (GB-D2). The existing GB pages stay on `dogma/payroll` (versions `v2.0`, `v1.0`, for example `G/API Pages/Pag70702745.SIRGBFiscalYear.al`). The onboarding and posting slices still wrote `qnipay/workforce`; that is corrected. A separate group keeps entity set names such as `employees` from clashing and keeps the Workforce pages movable. Base's only API page today is `SIR Frequency Setup API` (`B/API/Pag70702654.SIRFrequencySetupAPI.al`).

Workforce calls no `dogma/payroll` page (GB-D15). The foundation slice had the tenant read take the financial year and pay frequency from GB's `fiscalyears` and `payfrequencies`, and the timesheet slice had /home take bank holidays from GB's `baseCalenderChanges` and site names from `worksites`. Base cannot depend on GB pages (W1 tenants have none), and they lack Workforce's fields and checks. So 70703151 `SIR_WF API Workforce Setup` exposes the active financial year and the default pay frequency read only, and 70703155 `SIR_WF API Bank Holidays` and 70703172 `SIR_WF API Work Sites` serve the rest.

### 2.4 Commands

03 used command entity sets only, on the belief that bound actions take no parameters. GB proves otherwise: `[ServiceEnabled] procedure GetPayslip(systemId: Text): Text` on an API page (`G/API Pages/Pag70702818.SIRGBPayslipAPI.al:108-117`). The ruling (GB-D4):

- **Where a record exists**, the command is a bound action with parameters on that record's entity page. The trial confirms it works with service-to-service sign-in.
- **Every other command** goes through one generic API page, `commands` (70703150 `SIR_WF API Commands`), over the temporary table 70703166 `SIR_WF Command`. Inputs: `command`, `sessionId`, `correlationId`, `idempotencyKey`, `version`, `payload` (JSON text). Outputs: `result`, `recordId`, `recordIds`, `auditId`, `warnings`, `summary`, `message`. It dispatches by enum 70703150 `SIR_WF Command Type`, which implements the interface `SIR_WF Command Handler`, one codeunit per command.
- **Why one page:** page IDs in Base are scarce, and Node already validates every payload with zod.

Applying it beyond the slices' own split:

- Bound actions go through the same dispatcher and enum, with one five-parameter signature, so gates, audit, idempotency and refusals are identical on both paths (GB-D12).
- Command entity sets that act on one existing record became bound actions: the timesheet day transition, the timesheet config save, the clock close, the onboarding config, policy, case, document and template operations, one notification read and the posting retry. The session commands stay on `commands`, because binding them would put the session id in a URL (GB-D14).
- Entity DELETE is replaced by a bound action `remove` (GB-D13): a DELETE has no body, and 03 §1.4's workaround (PATCH a write-only page variable, then DELETE in one changeset) fails because each request in a changeset gets a new page instance.

Result: 15 commands on `commands` and 33 bound command types on 27 entity sets (the single `remove` type serves 11 of them), so 48 command types and 48 handler codeunits (doc 13 §3–4).

### 2.5 Session and identity

GB has no session table (`SIR Approval Session` and `SIR Portal Gateway` do not exist; a grep of `Session`, `Portal`, `Entra` across all `.al` files finds none) and no Entra field (W1's `Employee."SIR Approver Entra Object ID"` is missing; the nearest field, `Employee."SIR Associated User ID"` Code[50], `B/Table Extensions/Tab-Ext70702579.SIREmployee.al:18`, links a BC user, and employees are not BC users).

- 70703152 `SIR_WF Account` holds the Workforce identity: email, Entra Object ID (set at first sign-in), employee, blocked. The user type lives on Employee (`SIR_WF User Type Code`, B14, GB-D24).
- 70703153 `SIR_WF Session` (the foundation slice's, GB-D6) holds one open session per account and the view-as. Its Guid is created by BC and held only by Node. Every write carries `sessionId` in the body or as an action parameter, never in a URL or `$filter` (B13). The timesheet slice's `sessionToken` header is renamed `sessionId`.
- QniConnect's portal users, `isAdmin` and registrations are in neither GB repo; whether `SIR_WF Account` replaces them is GB-Q10.

### 2.6 Public Id and Version

- **Reused coded tables** (Employee, `SIR Work Sites`, Dimension Value, Job, Job Task, `SIR TIme Sheet Elements`): no Public Id. Codes never change, so Node derives the contract id as `<prefix>_<code>` (`emp_`, `loc_`, `dep_`, `cc_`, `prj_`, `pc_`), with no backfill of thousands of GB rows. They get `SIR_WF Version`, which install sets to 1 and which is bumped only when a contract-mapped field changes, so payroll's own edits (BACS flags, RTI band) do not make React stale. The people slice's rule wins; the timesheet slice's Public Id on `SIR TIme Sheet Elements` is dropped (GB-D3).
- **New `SIR_WF` tables** keep 9900 Public Id and 9901 Version (01 §4.2), with listed exceptions: temporary tables; the session and idempotency tables; child rows versioned through their parent; append-only logs addressed by Entry No.; and tables whose key is itself a lower-case contract id or whose contract id is longer than Text[50] (account `acc_<email>` up to 84 characters, onboarding policy up to 84, onboarding template up to 68, template key up to 100). The people slice's new master tables (job profile, employee type, profile change) do carry Public Id, filled with the id Node would derive (GB-D11). Doc 11 states per table which it carries.

### 2.7 Business Central versions

Both apps declare `"application": "27.0.0.0"` and `"runtime": "15.0"` (`Qnipay-base/app.json`), but the symbols in both `.alpackages` folders are Microsoft Base Application **29**.0.54011.56136 (and System 29.0.56111.0). Code written against these symbols can use objects, fields or enum values that a version 27 tenant does not have, and the compiler will not say so. The onboarding reviewer checked the `Employee Gender` values against 29 (MS `EmployeeGender.Enum.al:12-31`) and asks that they be checked against 27 too. Which version is the floor, and whether the symbols should be pinned to it, is GB-Q36.

### 2.8 Licensing

Workforce follows QniConnect's model: the employee signs in to Entra and talks to Node; Node calls Business Central service to service with one app registration; the employee is a portal user, never a BC user (doc 13 §1.2). An app-only identity does not consume a user licence, but Microsoft's licensing rules on multiplexing say that pooling access through a service does not reduce the number of licences needed: users who use Business Central data through the connector may need their own licence. QniConnect already reaches payslips this way; Workforce widens it to about 500 people writing timesheets, clocking and onboarding data. If a licence per person is needed (Team Members at the least), the cost changes, and if the calls must then be made as each user, the connector design changes (05 R19). This needs a written answer from Microsoft or the licensing partner before phase 2 (06 P3; GB-Q37, GB-Q38). Separately, module licensing (B11, P8) is undecided; GB already has `SIR_GB License Detail` 70702719 and `SIR_GB Subscription Detail` 70702720 (`G/Licensing/`) and Base has `SIR Product Setup` 70702604 with a License Key Blob (`B/Administration/Tab70702604.SIRProductSetup.al:23`), worth checking before a new mechanism is chosen (GB-Q21).

## 7. Posting approved hours to payroll

GB's inbound path supports the design in outline: an interface row per approved day, pay code and site, picked up by a payroll user's **Create Time Sheets** run, merged into released timesheet lines, and read by the payroll calculation by pay period. Payroll reads timesheet lines by period, not by header, so Workforce can drip rows in all month and payroll can run Create Time Sheets as often as it likes. But the GB interface is older than W1's, and three things bite harder than in W1: no pay period on the row (G), Daily mode as the default (B), and the rate as a manual payroll step (A). Posting is all Base and Workforce; no GB change is needed for hours posting (no GB subscriber touches the interface, the report or the lines). GB's only involvement is downstream: holiday pay hours and the Timesheet Adjustment.

**Create Time Sheets.** Request page: Timesheet Type (Daily/Period), Frequency, Fiscal Year, Period, Irregular; `SaveValues = true` (`Rep70702584:21`); `TimeSheetType: Option Daily,Period` (`:506`), so a fresh run defaults to Daily. `CreateTSHeader` (`:146-177`), under `ErrorBehavior::Collect`: refuses if an **Open** header exists for the same dates (`:154`, `:345-357`), so the report can run many times per period; takes **every** row with `Is Timesheet Created = false` (`:309-311`), with no filter on date, frequency, period or irregular; collects errors for blank fields and **zero Rate** (`:470-473`); skips **silently** a Site Code that is not a work site (`:460-461`); does not check active or terminated status (`IsActiveEmployee`, `:403-412`, unused); creates missing employee sites (`:94-144`); Period mode merges into one line per employee, document, dates, rate, element and site (`:222-269`) and raises `OnBeforeInsertTimeSheetLine` (`:261`) or `OnBeforeModifyTimeSheetLine` (`:266`); Daily mode creates one line for **every day of the period**, each with the row's full units (`:271-301`, `:296`), with no event; sets `Is Timesheet Created` (`:338-340`). ### 7.3 Decisions on the path

Posting uses the interface path (B1). Workforce pre-checks everything Create Time Sheets checks and everything `Validate("Site Code")` could create (doc 12 §6.2), so a Workforce row can neither stop the payroll run (H) nor create master data (F). Late days fail with `PERIOD_POSTED` and are never moved to another period silently (GB-D66).

### 7.4 The second inbound path (not chosen)

GB also exposes `dogma/payroll/v2.0` pages over `SIR Timesheet Header`, Line and Employee (`G/API Pages/Pag70702756-70702758`). With `Enable Timesheet Interface` off, hours go into custom fields 5000–5019 and payroll prices them itself, so no rate ever sits on the row. It is company-wide and exclusive with the interface path (`Tab70702583:2204` against `:2230`). It is listed only as an option for the payroll owner (GB-Q25).
